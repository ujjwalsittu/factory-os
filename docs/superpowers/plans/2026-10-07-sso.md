# Configurable Google and Microsoft SSO Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Existing FactoryOS users explicitly connect Google/Microsoft identities and sign in through them while preserving local TOTP, password recovery and current tenant permissions.

**Architecture:** Native Better Auth providers own OAuth protocol validation; focused server policy owns identity/consent/callback boundaries. Additive account/action/event/session metadata and PostgreSQL triggers make binding mutation and evidence atomic. A typed wrapper extends the existing twoFactor hook and carries binding provenance through its real challenge lifecycle; providers stay disabled until verified rollout.

**Tech Stack:** Existing Node24.19/pnpm10.28, NestJS12, Better Auth/core/drizzle-adapter1.7.7, Drizzle0.45.3/PostgreSQL, Next16.3.8, JOSE6.2.12. No new provider service, library upgrade or production fixture bypass.

**Spec:** `docs/superpowers/specs/2026-10-07-sso-design.md`, decision043; user Continue2026-10-07 approves the written spec only. User approved this plan2026-10-07; Native execution claimed.

## Global Constraints

- Google and Microsoft can be enabled independently per deployment. Both disabled by default.
- First release signs in existing explicitly linked accounts. Both native providers set `disableSignUp:true`; caller `requestSignUp:true` must not bypass it.
- No implicit linking, even for matching verified emails. `disableImplicitLinking:true`, `allowDifferentEmails:false`, `updateUserInfoOnLink:false`.
- Connecting requires a locally verified email, a live session created within5 minutes, password confirmation and the existing completed TOTP/trusted-device policy when enabled.
- Microsoft targets one explicit organization UUID; common/organizations/consumers refused. Google checks signed hosted-domain claims when restricted.
- Google requests only openid/profile/email. Microsoft overrides defaults to openid/profile/email, sets disableProfilePhoto:true and requests neither User.Read nor offline_access.
- Use native authorization-code redirect flow only. Reject client-supplied idToken, arbitrary scopes/additionalParams/client-certified security context; preserve PKCE/browser state binding/token checks.
- Token material is encrypted with native encryptOAuthTokens:true and account cookies are disabled. Block browser get-access-token/refresh-token/account-info routes.
- No provider identity changes memberships, roles, platform privilege, local email/verification/name or shared business ledgers. Existing password credentials cannot be disconnected in this phase.
- Native inline/default branch is already selected. No new worktree, method question, implementer/per-task agents or live OAuth registration/sends. One final independent review only after Task8; one Critical/Important correction pass, defer Minors with reason/cost, no second review.
- Original SQL0011–0024 and saved original activation rows are immutable. Capture SSO baseline once before mutations; never recapture it after changes. Claims/TTL checks use fresh time after waits.
- Root checks run from repository root with PATH=/workspace/.factoryos-tools/node_modules/.bin:$PATH. Build finishes before production browsers. Shared signup suites serial/paced12 seconds; fixtures default API4000/web3000 and support overrides.

## Review Focus

1. Matching emails, stale/foreign link consent and concurrent callbacks must never merge or transfer a local account — Tasks2/3/4/7.
2. Native provider callbacks and direct auth endpoints must not bypass existing TOTP, browser state binding, same-origin returns or local-session revocation — Tasks4/5/7.
3. Provider configuration/issuer changes, signed hosted-domain/tenant restrictions and changed profile emails must not authenticate a stale or foreign binding — Tasks1/4/5/7.
4. Provider tokens, codes, state and action proof must stay encrypted/redacted; failed mutation evidence must not leave unaudited identity authority — Tasks2/4/5/7.
5. Account switching, invitation returns and current tenant membership/role checks must preserve existing access boundaries without ledger/book changes — Tasks5/6/7/8.

## File boundaries and shared interfaces

Create API `modules/sso/{sso.types,sso.config,sso.urls,sso.store,sso.service,sso.policy,sso.mfa,sso.controller}.ts`; config/types/URLs are pure, store owns DB records, service owns consent/ownership, policy owns native hooks, MFA wraps the installed plugin, controller injects AUTH without a service→AUTH cycle. Modify existing auth/config/AppModule/access only at integration points. Add DB `schema/sso.ts` plus server-only auth fields; web `components/sso/` holds provider/security UI. Do not refactor unrelated authentication/business controllers.

Task1 exports `SsoProviderId='google'|'microsoft'`, `SsoActionKind='link'|'unlink'`, `SsoConfig={google:null|{clientId:string;clientSecret:string;allowedHostedDomains:string[]};microsoft:null|{clientId:string;clientSecret:string;tenantId:string;issuer:string}}`, `SsoReturn=string` (validated relative path) and `SsoAuthFrame={mode:'signin'|'link'|'mfa';provider:SsoProviderId;userId:string;accountId:string|null;issuer:string;returnPath:SsoReturn;actionId?:string}` (null accountId only before a new explicit link). The frame is stored on the native per-request context under a private Symbol, never taken from body/additionalData.

Task2 exports DB `authSsoAction` and `authSsoEvent`, account `ssoIssuer/ssoActionId`, session `ssoAccountId/ssoIssuer/ssoPending`, verification `ssoAccountId/ssoIssuer/ssoReturnCipher`. Metadata is optional for old credential sessions/verification records, server-input-only and never publicly returned. Verification fields use a plugin schema extension: installed getFields only reads top-level additionalFields for user/session/account, but supports plugin schema.verification fields. No unsupported verification.additionalFields option.

Produce `SsoStore` with constructor `(db:Database,config:AppConfig)`. Store methods: `createSsoAction(ctx:RequestContext,input:{provider:SsoProviderId;kind:SsoActionKind;targetAccountId?:string}):Promise<{nonce:string;expiresAt:Date}>`; `validateSsoAction(ctx:RequestContext,nonce:string,input:{provider:SsoProviderId;kind:SsoActionKind;targetAccountId?:string}):Promise<SsoActionRecord>`; `prepareUnlinkReference(ctx,action:SsoActionRecord):Promise<void>`; `completeSsoSession(sessionId:string,frame:SsoAuthFrame):Promise<void>`; `pruneSsoActions(limit?:number):Promise<number>`. `SsoActionRecord` is the exported DB select type. None accepts a caller's target user ID or issuer as authority.

Service: `SsoService(db:Database,config:AppConfig)`; `availability():ProviderAvailability[]`; `listMethods(ctx:RequestContext):Promise<ConnectionSummary[]>`; `issueAction(ctx,input,passwordVerified:()=>Promise<boolean>):Promise<{nonce:string;expiresAt:Date}>`; `authorizeOAuth(data:NativeUserValidation,ctx:NativeContext):Promise<void|{error:string}>`. Task1 defines `ProviderAvailability={id:SsoProviderId;label:string}` and `ConnectionSummary={bindingId:string;provider:SsoProviderId;label:string;connectedAt:string}` (ISO timestamp); native types derive from installed BetterAuthOptions.user.validateUserInfo, not invented any types.

Policy: `buildSsoOptions(db:Database,config:AppConfig):Pick<BetterAuthOptions,'socialProviders'|'account'|'session'|'user'|'hooks'|'databaseHooks'>`; `withSsoMfa(plugin:ReturnType<typeof twoFactorPlugin>,store:SsoStore,config:AppConfig):BetterAuthPlugin`. Final factory explicitly merges existing email hooks/schema/options; no overwriting callback privacy behavior or recursive AUTH injection.

# Bank Reconciliation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans for the user-selected Native execution. Implement inline, task by task, then use one fresh independent final reviewer; no implementer agents. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver configurable statement imports, exact matching and reviewed bank reconciliation without changing ledger amounts through matching.

**Architecture:** Pure parsing/arithmetic consumes immutable statement and bank-entry evidence. Scoped import, match and report services write append-only evidence under the existing entity accounting lock. A dependency guard used by GL posting/reversal protects baselines, active matches and approved reports; exception posting delegates existing charge/manual-journal paths.

**Tech Stack:** TypeScript, existing exact `Dec`/BigInt, NestJS/Zod, Drizzle/PostgreSQL, Next.js/React Query and `@factoryos/ui`; existing pnpm10.28/Node>=22. No new provider or storage dependency.

**Spec:** `docs/superpowers/specs/2026-10-06-bank-reconciliation-design.md` (written spec approved by user Continue2026-10-06; decision041 Accepted).

## Global Constraints

- Native execution on the existing default branch; user already selected the method. Claim product implementation in STATUS, commit and push before product code.
- INR bank profiles only. Foreign party settlements remain matchable by actual INR bank GL; foreign bank statements are refused.
- Matching/unmatching alone writes no GL, bill, stock or FIFO effect. Match bank debit−credit, never settlement principal or expense lines.
- UTF-8 CSV first:5MiB and10000 transaction rows maximum; quoted/multiline/BOM supported. No Excel/PDF/OCR/OFX/feed or new credentials.
- Dates, signs, decimal/group separators and source ordering are explicit mappings, not guesses; amounts are decimal strings up to six places. Suggestions use date distance0–30days, default7; reference normalization trims whitespace/folds case only.
- Baseline date on/after accounting cut-over; `B0−sum(O0)=S0` exactly. Opening evidence adds no GL or shared activation.
- Ordinary matching uses same-sign positive allocation edges; Finance net groups use signed side vectors, nonzero equality and whole-group reversal/date effectiveness.
- Report difference is `S−(B−U+E)`. Zero difference alone is insufficient: complete coverage, no unresolved duplicates/bank-only items and Finance-reviewed outstanding list are required.
- Approved bank intervals protect bank posting/reversal and evidence changes; no new global period lock. Historical reports are immutable revisions with explicit Finance reopening.
- Add migration after0019; preserve0011–0019 bytes and preexisting activation states. Apply only to local integration fixtures, not deployed/shared Finance activation.
- All queries/IDs tenant/entity/profile scoped; permissions and original charge/journal rules remain authoritative. Audit hashes/reasons/counts, not raw bank text. Spreadsheet exports escape formula prefixes.
- API scripts default API4000/web3000 with `API`/`WEB_ORIGIN`; browser scripts support `WEB_URL`/`CHROMIUM_PATH`. Existing local overrides4001/3001 usable; pace fresh signup suites12seconds.

## Review Focus

1. Legitimate repeated same-day/reference/amount transactions and reordered/overlapping CSV files must neither disappear nor be counted twice — Tasks1/4.
2. Quiet periods, overdrafts, reversed source order and transactions straddling book/bank dates must retain correct coverage/sign/as-of balances — Tasks1/7.
3. Custom nested bank ledgers, inactive historical accounts and duplicate opening links must not select another ledger or replay old GL — Tasks2/3/5.
4. Concurrent residual use, source cancellation or repeated exception clicks must have one atomic outcome with no partial ledger/evidence — Tasks5/6/9.
5. Files larger than JSON's default body limit, malformed UTF-8/quotes, formula text and late previews after account/entity changes must remain safe and usable within the declared limits — Tasks1/4/8.

All API signature shorthand below uses `ctx:TenantRequestContext`, `entityId:string` and UUID-string profile/import/group/period IDs; validation is strict Zod at the boundary. API net-match request supplies IDs/reason only; the server derives its pure source evidence from the actual settlement/charge/voucher, never from client assertions. DB row return types are named `BankProfile`, `BankBaseline`, `StatementImport`, `MatchGroup`, `BankPeriod` inferred from new tables.

Pure `bank-reconciliation-types.ts` defines `CsvMapping`(specified columns, separators, date format, ordering and balance-only row selector), `StatementParseInput`(CSV text plus stated period/opening/closing), `NormalizedStatement`(original ordinals/normalized date/signed amount/reference/description/optional transactionId/runningBalance, ignored balance rows, totals/errors), `StatementItem`(canonical id, date, signedAmount, reference); `BookItem`(kind gl/opening, id, date, signedAmount, reference, source evidence), `OrdinaryMatchInput`(edges of statementRowId/bookItemKind/bookItemId/positive amount), `NetMatchInput`(whole statement IDs, one settlement bank GL ID, source evidence, reason), `ResolvedMatch`(ordinary edges or net side vectors plus effective dates), `ReconciliationInput`(baseline, dated book/statement movements, active resolved matches, coverage). Exact field names/types used in implementations must match these declarations; no database dependency in core.
